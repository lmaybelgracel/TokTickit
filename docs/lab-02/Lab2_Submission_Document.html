Answer Part 2: Spec DD (Specification-Driven Development) 5 คะแนน

Link to Specification: docs/lab-02/specification.md

2.1 โครงสร้างเอกสาร Engineering Specification (ครบถ้วน 11 Sections ตามข้อกำหนด 8.10)

  1. Sprint Goal: ส่งมอบระบบ Requester Ticketing MVP ที่ให้ผู้ใช้งานสร้างตั๋ว ค้นหา จัดการไฟล์แนบ ภายใต้ระบบจำลอง Development Requester และดีไซน์ Zen Green
  2. Stakeholder Request Interpretation: วิเคราะห์ขอบเขตงานจาก Stakeholder อย่างเป็นระบบ
  3. Scope: ระบุ Included และ Excluded ชัดเจน (ไม่รวม Auth จริง, IT Staff workflow, Comments)
  4. Functional Requirements: กำหนด FR-01 ถึง FR-13 ครอบคลุม Requester Context, Ticket Creation, My Tickets, Ticket Detail และ Attachment Lifecycle
  5. Business Rules: กำหนดกฎธุรกิจหมายเลข BR-01 ถึง BR-11 (เช่น รูปแบบ Ticket Number, ขีดจำกัดไฟล์ 5MB/5ไฟล์, Soft Removal พร้อมเหตุผล 3-250 ตัวอักษร, Atomic Database Transaction)
  6. UI Specification Summary: สรุป Zen Green Palette, Badges, Layouts
  7. Data Changes: กำหนด Prisma Schema ครบทั้ง 5 Models พร้อม Foreign Keys และ Indexes
  8. API Contract: กำหนด Endpoints, Context Header X-Development-Requester-Id, Payload shapes, และ HTTP Statuses
  9. Acceptance Criteria: กำหนดในรูปแบบ Given-When-Then หมายเลข AC-01 ถึง AC-09
  10. Definition of Done: แบ่งเป็น Product Completion และ Course Delivery Checklist
  11. Assumptions and Decisions: บันทึกข้อตัดสินใจทางเทคนิค เช่น LocalStorage persistence และ Server disk storage
หลักฐานการทำ Spec DD ก่อนเริ่มเขียนโค้ด: เอกสาร specification.md ถูกจัดทำและเปิด PR แรก (PR #23) ก่อนเริ่มงาน Database, API หรือ Frontend ใน Issue ถัดไปตามแนวทาง Spec-Driven Development

6.1 ข้อกำหนดหลัก 5 ประการที่ผ่านการตรวจสอบ

  1. Requester Field Populated: ฟิลด์ชื่อ Requester ถูกดึงมาจากผู้ใช้งานที่เลือกไว้ในระบบจำลองอัตโนมัติ และตั๋วที่บันทึกมี requesterId ตรงกัน
  2. Reference Data Loaded: หมวดหมู่ (Categories) และระบบที่เกี่ยวข้อง (Related Systems) โหลดมาจาก PostgreSQL อย่างถูกต้อง
  3. Field-Level Validation: เมื่อกรอกข้อมูลไม่ครบหรือสั้นเกินไป ระบบแสดงข้อความแจ้งเตือนสีแดงใต้ฟิลด์นั้น ๆ ทันที
  4. Attachment Constraints: ทดสอบอัปโหลดไฟล์ที่ถูกต้อง (ผ่าน) และไฟล์เกินขนาด/ผิดประเภท (ถูกปฏิเสธพร้อมข้อความเตือน)
  5. Form Value Retention on Error: เมื่อเกิดความล้มเหลวในการส่งข้อมูล ค่าต่าง ๆ ที่ผู้ใช้กรอกไว้จะไม่สูญหาย

ภาพที่ 6.2: หน้าจอ Development Requester Selection Screen แสดงเฉพาะ Active Requesters
ภาพที่ 6.3: การแจ้งเตือน Field-level Validation Messages บนหน้าจอ Mobile เมื่อไม่กรอกข้อมูลสำคัญ
ภาพที่ 6.4: การปฏิเสธไฟล์แนบที่มีขนาดเกิน 5 MB หรือนามสกุลไฟล์ไม่ถูกต้องตามกฎ BR-05

8.1 วงจรชีวิตของไฟล์แนบและการรักษาความปลอดภัย

  • Read-only Detail: ข้อมูลตั๋วทั้งหมดแสดงผลแบบอ่านอย่างเดียว พร้อม Badges สีชัดเจน
  • Active File Download: ผู้ใช้ที่เป็นเจ้าของสามารถคลิกดาวน์โหลดไฟล์แนบที่ยังใช้งานอยู่ได้
  • Soft Removal: การลบไฟล์แนบถูกบังคับให้ระบุเหตุผล (3-250 ตัวอักษร) ไฟล์ไม่ถูกลบจริงจากฐานข้อมูล แต่ถูกเปลี่ยนสถานะเป็น isRemoved: true
  • Download Protection (410 Gone): ไฟล์ที่ถูกลบไปแล้วจะไม่สามารถดาวน์โหลดได้อีก ปุ่มดาวน์โหลดจะถูกล็อกพร้อมไอคอนกุญแจ
  • Cross-Requester Protection (403 Forbidden): หาก Requester อื่นพยายามเข้าถึงตั๋วหรือไฟล์ผ่าน URL จะถูกปฏิเสธด้วย HTTP 403 Forbidden
